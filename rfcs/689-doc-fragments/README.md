# Proposal: Named doc fragments, checked examples, and inline translations

Author(s): Mike S.

Last updated: 2026-11-27

Status: Draft

Discussion at https://github.com/temperlang/temper/issues/689

## Status

Authored by Claude based on two rounds of spoken notes from MVS.  Needs self-review.

This RFC is partly for discussion by the team.
Several parts could go more than one way, and the point is to hash out what we actually need.

## Abstract

Temper's documentation should stay true to the language while the language changes underneath it.

This proposal brings back the best parts of the first compiler's documentation pipeline, in a form that suits the new compiler and plain GitHub Flavored Markdown (GFM):

- **named doc fragments**: chunks of Markdown, delimited by HTML comments, that live beside the code they describe, mostly in std's and core's literate sources, and that docs pages, the REPL's `help`, and links can refer to by name;
- **cross-references**: `[Boolean]`-style links to declared entities, by their qualified names, and to fragments, resolved relative to where they appear;
- **checked examples**: Temper code blocks whose result, error messages, and logged output are checked by running them;
- **inline translations**: a Temper code block followed by its translation into another language, regenerated by the compiler, so prose can say "here's what that looks like in Python".

It also evaluates Docusaurus, MkDocs, and mdBook as the publisher for the docs site, against the site we build today with Kelpto.

## Background

### What the first compiler did

[temperlang.dev](https://temperlang.dev/) was generated from the first compiler's `docs/for-users/` tree, which was itself regenerated by `build-user-docs/`, an extensive doc extractor written in Kotlin ([kotlin-final](https://github.com/temperlang/temper/tree/kotlin-final)).
Its model was *snippets*:

- A snippet was a chunk of Markdown extracted from a doc comment in Kotlin or Temper source, or derived from one, such as a railroad diagram drawn from a grammar.
- A snippet started with `<!-- snippet: syntax/Arg : Short title -->` and ended at the next snippet, at `<!-- /snippet -->`, or at the end of the comment.
- Its ID was a `/`-separated path, which also named the file it was written to.
- Skeletal docs pages pulled snippets in with an insertion line, `⎀ syntax/Arg`, optionally marked as the snippet's canonical location.
- A link like `[snippet/syntax/Arg]` was rewritten to point at the canonical location, using the snippet's short title as the link text.
- `.snippet-hashes.json` recorded a hash of each snippet so CI could tell when the docs were stale.
- Builtins carried snippet IDs as metadata, so the REPL's `help` could recall a builtin's docs by name: `help(ignore)` found `snippet/builtin/ignore`.
  Function values carried that metadata at run time.
- Operations over sets of snippets were possible.
  The builtins reference was assembled by enumerating every snippet whose ID started with `builtin/`.
- The build wrote a big JSON file of snippets, which the REPL loaded as a resource, so `help` could look them up.
- Examples were run through the REPL, and the generator filled in each one's marker and result value, so the docs showed what actually happened.

That model of modular documentation was nice.
A doc's chunk had one home, next to the code, where a developer changing the code would notice it.
Its place in the eventual book was a matter of naming it, not copying it.

It was also a bit complicated, and much of the complication came from extracting Markdown from Kotlin source.
This proposal keeps the model and drops that part.

### What the new compiler does

The new compiler's docs, under `docs/`, began as that generated output, imported once and edited by hand since (see `docs/contributing/docs.md`).

- **Examples are partly checked.** `compat/check_doc_examples.py` runs each ```` ```temper ```` block on the interpreter and checks its last-line marker: `// ✅` must run cleanly, `// ❌` must fail, and `// ⏸️` isn't run.
  `//!outputs "…"` comments say what a block logs, and those are compared.
  The values after `✅` and the errors after `❌` aren't compared yet, and tutorial steps that build on earlier ones can't be run.
  Fourteen examples are known to disagree with the compiler (inconsistency I10).
- **The site** is built by `site/docs/build.py` with [Kelpto](https://github.com/temperlang/kelpto), our lossless GFM library written in Temper and translated to Python.
  The build adds heading anchors, GFM alerts, Temper highlighting, a sidebar, Mermaid diagrams drawn to inline SVG, and a link check against git's own objects.
  It has no search yet.
- **The REPL's `help("name")`** shows a declaration's signature and doc comment.
  `translate(n, lang)` shows an earlier input translated into one of the backends' languages.
- **`temper doc`** is listed by `temper help` but not available yet.
- **The std reference pages** (`docs/std/*.md`) are hand-kept.
  They repeat what std's literate sources (`lib/std/*/*.temper.md`) already say, so the two can drift apart.

The port picked up lots of examples and documentation from the original, but nothing keeps them true.
I worry that the docs site and the language will drift apart right when we are plumbing in important changes, like RFC 164's failures and RFC 684's flat options.

### Goals

Our documentation includes the language reference, how-to documentation for the language, and documentation for the standard library and core.
All of it should be maintainable alongside the compiler.

1. **Mostly Markdown.** We keep writing most of our documentation as Markdown files, plus the Markdown in literate `.temper.md` sources.
2. **GFM all the way down.** GitHub Flavored Markdown is what works for our READMEs, and it's well understood.
   The tools should be GFM compatible, so nobody switches back and forth between two Markdown variants.
   Every source file reads well on GitHub as is, and the same files make the site, as `docs/contributing/docs.md` requires today.
   Any syntax we add must be invisible or harmless where GitHub renders it.
3. **Polish.** Language documentation is often someone's first experience of the language community, maybe working through a getting-started page.
   If the docs don't look like we put care and effort into them, a newcomer might conclude "this isn't for me": if these people can't be bothered to write good docs, why give the language a spin?
   For early adopters and learners, polish matters.
   Much of it comes from a good Markdown-to-HTML tool: good styles, a table of contents, and the bells and whistles you don't need every day but are glad of when you do.
4. **Transparency.** A doc fragment lives next to what it describes, so a change to the code is visibly a change near its docs.
5. **Addressable by name.** A fragment has a stable identifier that docs pages, links, and the REPL's `help` can use, independent of which page it appears on.
   Declared entities already have one: their qualified name.
6. **Cross-references by structured names.** Like Javadoc's references to types and methods, a page can link to an entity by name, with short link text picked for it, and with names resolved relative to where the reference appears.
7. **Examples that are live.** Temper code examples shouldn't rot as the language changes.
   Usage examples, and examples of what not to do, are checked by running them, so people can trust them as reflecting what the compiler and interpreter actually do.
   That way nobody has to crawl over the docs to figure out what to update after a breaking change.
   As we add deprecation warnings, they point us at examples in a style we no longer recommend.
8. **Translations in the flow of the docs.** Temper translates to other languages, so its docs need to talk about those languages too, and it'd be good to have compiler checks for that talk.
   A page can show some Temper and then its translation, regenerated from the compiler, not pasted in.
   For example: "Here's how to do this in Temper: [TEMPER CODE]. That translates to the Python below, so you can see how string indices in Temper just correspond to Python ints: [PYTHON TRANSLATION]."
   Or, in `std/temporal`'s docs: "Here's an example using the `Date` type from Python.  You can see that it uses Python's built-in `datetime`, because that's how the Python backend connects it."
9. **Beyond std.** What we do for std and core should extend to other libraries.
   Other libraries will need to make arguments like "if you're using this from Python, here's how", and documentation assembled from several sources, with coherence checks and conveniences built in, would help them too.
   I suspect power users will lean on this most, but not only them.

### Non-goals

- Extracting documentation from the compiler's own source code, as the Kotlin extractor did.
  It might be nice to have, but preserving that property isn't a goal.
- A complete `temper doc` for third-party libraries.
  That's a separate proposal, but this proposal's conventions should be the ones it uses.
- Translating the docs into other human languages.

## Proposal

This proposal consists of these parts, each of which has its own heading below:

1. **Fragment markers**: HTML comments that delimit and name blocks of Markdown in `.md` and `.temper.md` files, and in doc comments in `.temper` files.
1. **Declaration fragments**: an implied fragment for each documented declaration, named by its qname, so std's and core's autodoc comments are addressable without markers.
1. **Materialized inclusions**: a docs page includes a fragment, or every fragment under a prefix, between marker comments, and the included text is committed, checked to be current, and regenerated by a tool.
1. **Cross-references**: `[Boolean]`-style links to entities and fragments, resolved relative to where they appear, and materialized as ordinary link definitions.
1. **Checked examples**: finish what `check_doc_examples.py` started, add `temper example` blocks and continued sessions, and move it into `temper`.
1. **Inline translations**: a Temper block can ask for its translation, which is materialized after it like an inclusion.
1. **REPL help by fragment name.**
1. **A publisher** for the site.

All of this is tooling.
None of it changes the Temper language.

### Fragment markers

A fragment is a run of whole Markdown blocks between an opening and a closing comment:

```markdown
<!-- doc: std/json/producers : Producing JSON -->

A `JsonProducer` receives a stream of events …

    export interface JsonProducer { … }

<!-- /doc -->
```

- **The name** is a `/`-separated path, as snippet IDs were.
  Each part is non-empty and has no spaces, control characters, `/`, `\`, `;`, `:`, or `.`.
  By convention the first parts name where the fragment lives: `std/json/…`, `core/…`, `language/…`, `repl/…`, `builtin/…`.
  Leaving out `.` keeps these names apart from qnames (see *Declaration fragments*), which always have one.
- **The short title**, after a second colon, is optional.
  It's the default text for links to the fragment.
  Without one, a fragment that starts with a heading uses that heading's text.
- **Where it ends.**
  As in the first compiler, a fragment ends where the next one starts, or at the end of its doc comment or file.
  When it should end sooner, and doesn't end at the start of another fragment, an explicit `<!-- /doc -->` ends it.
- **Nesting** needs explicit ends: a fragment that contains another has a `<!-- /doc -->` for the inner one before the outer one's.
  The outer one includes the inner one's text.
  Fragments never overlap.
- **Markers are block-level.**
  Each sits on its own line, between blocks, as an HTML block in GFM terms.
  Extraction works on the parse tree, not on raw text, so a `<!-- doc: … -->` shown inside a code block, like the one above, isn't a marker.
- **In literate `.temper.md` files**, a fragment can span prose and code.
  When it's included elsewhere, indented Temper code becomes a ```` ```temper ```` fenced block, so it's highlighted and, if marked, checked.
- **In `.temper` files**, such as `lib/core/core.temper`, markers go inside doc comments, as they did in Kotlin and Temper doc comments before.

HTML comments are invisible on GitHub and in most Markdown renderers, so a source file with markers reads as it did without them.

### Declaration fragments

std's and core's literate files are full of declarations, and those declarations have autodoc comments.
In literate Markdown, the convention is: if one or more of the Markdown paragraphs before a named declaration start with that name, compared case-insensitively and ignoring Markdown meta-characters like `` ` `` and `*`, then the first such paragraph and the paragraphs after it, up to the declaration, are its autodoc comment.
Only paragraphs in the chunk of Markdown before that declaration, and not before a closer declaration, count.
Outside Markdown, a `/** … */` comment before a declaration is its autodoc comment, following the Java convention.

Each declared entity, whether a type, a function, a method, a property, or a parameter, also has a qualified name, or *qname*.
A qname starts with the library's name and the module's directory, then names each enclosing declaration, marked by its kind.
These are the same qnames the backends already use to connect core and std to their host languages, and that `temper.keep` will be keyed by (see the new compiler's `notes/tmpl/names.md`):

| Entity | Qname |
|---|---|
| a type | `core.type Boolean` |
| a method | `std/json.type JsonProducer.startObject()` |
| a parameter | `std/json.type JsonProducer.objectKey().(key)` |
| a top-level function | `std/json.parseJsonToProducer()` |

So we have an association between autodoc comments and declared entities, each with a ready identifier.
Each documented entity gets an implied fragment, with no markers needed:

- its name is the entity's qname;
- its content is the autodoc comment, followed by the declaration's signature as a Temper code block.

Explicit fragment names can't contain `.`, so they never collide with qnames.

Declaration fragments are what the REPL's `help` already shows, now with a name that the docs can share.

### Materialized inclusions

A docs page includes a fragment between a pair of comments, with the fragment's current text committed between them:

````markdown
## Producing JSON

<!-- include: std/json/producers -->

A `JsonProducer` receives a stream of events …

```temper
export interface JsonProducer { … }
```

<!-- /include -->
````

Because the included text is in the file:

- the page reads correctly on GitHub, in an editor, and in any publisher, with no build step;
- a change to a fragment shows up, in review, as a diff in every page that includes it;
- a checker fails when the text between the markers isn't what the fragment says now, and the same tool with `--fix` rewrites it.

This replaces `.snippet-hashes.json`.
The committed text is the record, and staleness is a diff.

Inclusion options go in the opening comment:

- `-heading` drops the fragment's leading heading when it would repeat the page's own;
- `+1` shifts the fragment's headings one level deeper, to nest under the page's;
- `canonical` marks the inclusion as where links to the fragment should go, if the fragment is included in more than one place.

Inclusions may nest, as fragments include their own inclusions, and a cycle is an error.

**Including a set.**
A reference page is mostly a list of entities, assembled in order, as the first compiler built its builtins page from every `builtin/` snippet.
`<!-- include-each: builtin/ -->` includes every fragment under a name prefix, and `<!-- include-each: core.type Boolean.* -->` every documented member of a type, sorted by name, each under its own heading.
Like any inclusion, the result is committed, and a new builtin shows up in review as a new section.

This is also how long-form docs and reference docs come together into one book: hand-written pages under `docs/`, with reference sections pulled in from std and core.

### Cross-references

When I'm writing about what `==` does, I need to refer to the `Boolean` type, and I'd like to do that by its identifier and get a link, with link text like *class Boolean*, without looking up which page it's on.
Markdown's square-bracket syntax is the natural place for that:

```markdown
The result of `==` is a [Boolean].  See also [`Map.get`] and [std/json/producers].
```

GitHub shows an unresolved `[Boolean]` as literal text, so the tool *materializes* the links: it adds a link reference definition for each one at the end of the file, and fixes them when targets move.

```markdown
[Boolean]: ../language/types.md#class-boolean "core.type Boolean"
[`Map.get`]: ../language/types.md#mapget "core.type Map.get()"
[std/json/producers]: ../std/json.md#producing-json "std/json/producers"
```

On GitHub, those are working links, with the target's name as a tooltip.
The checker resolves each name to its canonical location (where it's included with `canonical`, else where it's included at all, else its source), and it fails if a definition is missing, points somewhere else, or names nothing; `--fix` rewrites them.
So a fragment can move between pages, or a page can be split, without breaking links.

The first compiler's `[snippet/foo/bar]` links were rewritten when the site was built, so on GitHub they were broken links.
Materialized definitions work unprocessed.

**Relative names.**
The shorter and more concise a reference is, the better, but it must be possible to disambiguate when needed.
A reference appears somewhere, and that context resolves it, from the nearest scope out:

1. inside an autodoc comment, the documented declaration's own parameters and type parameters: "adds [x] and [y], then divides by [z]";
2. members of the enclosing type, so a method's docs can say "like [get], but …" without naming the class;
3. declarations in the same module, then the same library;
4. what the module imports, then core;
5. fragment names.

A name that resolves two ways at the nearest scope where it resolves at all is an error, which a more qualified name fixes: `[Map.get]`, or the whole qname.
Markdown files under `docs/` have no enclosing declaration, so their references start at step 4 with core and std's modules visible.

**Link text.**
An author's text is kept.
A link written with empty text, `[][core.type Boolean]`, gets text chosen for its kind of target and filled in by `--fix`: a type's name in a code span, a fragment's short title or first heading.

### Checked examples

Being able to run code samples is really important for keeping the docs healthy.
Our convention, from before, is that by default a code sample works: it completes with no compiler errors or warnings.
It can also be marked as producing a message, or computing a result, and a sample that logs to the console says what it logs in structured comments, which are compared with what it actually logs.

Most of this exists in `compat/check_doc_examples.py`.
The proposal is to finish it and to move it into `temper`, as `temper doc check`, so that it runs everywhere `temper` does, and library authors can use it on their own docs:

- **Examples in literate files.**
  In a `.temper.md` file, a ```` ```temper ```` fenced block is code: the compiler sees it as part of the module.
  ```` ```temper inert ```` is for code samples we never run.
  Neither fits an example of how to call the module's own API: "here's how you use this".
  ```` ```temper example ```` marks a documentation example.
  The compiler doesn't see it as part of the module, but the checker runs it in the module's context, so it can use the module's private helpers.
  (`usage` might read better than `example`; that's open.)
- **Unmarked means ✅.**
  Today an unmarked block runs, but failures aren't fatal, because tutorial steps build on one another.
  With continuations, below, that excuse goes away, and an unmarked example must run cleanly.
  So a deprecation warning fails the examples that use an older style, which is how they get found.
- **Compare values.**
  `// ✅ 42` checks that the block's last expression is `42`, as the REPL would show it.
- **Compare errors.**
  `// ❌ name not declared: x` checks that the block reports an error containing that text.
  A warning can be checked the same way, with `// ⚠️ …`.
  The first compiler filled in these values itself, and the checker's `--fix` can do the same, so writing an example doesn't mean typing its output.
- **Continued sessions.**
  Tutorial steps build on one another, like a pseudo-REPL session broken into chunks with prose in between.
  A block can say that it continues an earlier one, by name or by proximity:
  - ```` ```temper name=setup ```` names a block, and ```` ```temper continues=setup ```` runs after it, with its declarations in scope, as REPL inputs are;
  - a bare ```` ```temper continues ```` continues the nearest Temper block before it.
  
  Each block's marker is checked against the state built by the blocks it continues.
- **Backends.**
  By default examples run on the interpreter.
  `<!-- example-backends: py rust -->` before a block also runs it on those backends, which turns a docs example into a cross-backend test, like the `firstOrNull` example RFC 684 needs.

The `<!-- known: I10 -->` comments keep working as they do now.

### Inline translations

A Temper block asks for a translation with an attribute in its info string, and the translation is materialized after it:

````markdown
Here's how to do this in Temper:

```temper translate=py
let message = "Hello, world";
let i = message.next(message.next(String.begin));
console.log("${message[i]}");
```

That translates to the Python below, so you can see how string indices in Temper just correspond to Python ints:

<!-- translation: py -->

```python
message = 'Hello, world'
i = string_next(message, string_next(message, 0))
console_log(str(ord(message[i])))
```

<!-- /translation -->
````

- **The prose between them is allowed.**
  A translation belongs to the nearest preceding block that asks for that language, so an author can explain the translation before showing it.
- **By name, too.**
  `<!-- translation: py of setup -->` is a placeholder for the translation of the block named `setup`, wherever it appears on the page.
  So the Temper can come first, then a few paragraphs, then "and here it is in Python".
- **What it's for.**
  Since our translations are now fairly idiomatic, prose can explain how names correspond, how to use the translated library from your own Python code, and how std's types connect to the host's.
  For example, `std/temporal`'s `Date` is Python's `datetime.date`.
- **Translations are made the way the REPL's `translate(n, lang)` makes them**, and are checked and fixed like inclusions: committed, diffed in review, regenerated by `--fix`.
- **Selection.**
  A whole module's translation has imports, runtime setup, and wrappers that would bury the point.
  `translate=py select=greet` shows only the translation of the declaration `greet`.
  `select=top` shows only the top-level statements.
- **Several languages.**
  `translate=py,rust,js` makes one translation block per language, each wrapped in a `<details>` block, which is how the docs already show alternatives, one per language.

The code above is illustrative.
The real translation is whatever the compiler makes, which is the point.

A backend change that alters a translation makes a docs diff.
That's churn, but it's churn a reviewer should see: if a change makes the Python worse, the docs show it.
How many translations to keep is very much up to what the team wants to maintain.

### REPL help by fragment name

`help` already takes a declaration's name or value.
It also takes a fragment name, `help("std/json/producers")`, or a qname, and prints the fragment's text for the terminal, followed by the site address of its canonical location.

Builtins defined in the compiler, not in core, can name a fragment in their metadata, as the first compiler's did, so `help(console)` shows the same text as the docs.

As before, the build can write the fragment index for std and core as a JSON resource that `temper` embeds, so `help` works without the docs tree.

### Tools

Everything above needs a GFM parser that can find blocks and comments and rewrite a region of a file without reformatting the rest.

| Tool | Language | Notes |
|---|---|---|
| **Kelpto** | Temper, so any backend | Ours. Lossless: a parse prints back to the same text, so a tool can rewrite between markers and leave every other byte alone. Already renders the site. |
| [comrak](https://github.com/kivikakk/comrak) | Rust | A GFM-compatible CommonMark parser with a mutable AST, and an extension for GitHub's alerts. Not lossless: printing reformats. |
| [pulldown-cmark](https://github.com/pulldown-cmark/pulldown-cmark) | Rust | A pull parser with source offsets, which is enough to find markers and splice text. Used by rustdoc and mdBook. |
| [cmark-gfm](https://github.com/github/cmark-gfm) | C | GitHub's reference implementation of GFM. |
| [remark](https://github.com/remarkjs/remark) and the unified ecosystem | JavaScript | Markdown to an AST (mdast) and back, with many plugins. What Docusaurus uses. |

I propose Kelpto, translated to Rust and called from `temper`.
Being lossless is exactly what materialized inclusions and translations need, and Temper's docs maintained by a Temper library is the kind of dogfooding we want to show off.
pulldown-cmark's source offsets are the fallback if Kelpto's Rust translation isn't ready.

All the checks and fixes run as one `temper doc check [--fix]` over the docs, std, and core, in CI, and in CI's existing docs build before rendering.

### A publisher for the site

The goals above are independent of the publisher: once fragments, examples, and translations are materialized and checked in, the files are plain GFM, and any publisher can render them.
The question is what's best for publishing, given these requirements:

- **R1. Our GFM, unchanged:** GitHub alerts, `<details>`, Mermaid blocks, HTML comments, and relative `.md` links that work on GitHub too.
- **R2. A hook** for our own processing, in case some of it is better done at build time than committed.
- **R3. Temper highlighting**, ideally from the VS Code extension's TextMate grammar, which the site uses today.
- **R4. Search.**
- **R5. Toolchain fit:** the repo is Rust, with Python scripts and Node already needed for drawing Mermaid diagrams.
- **R6. Health:** maintained, with a future.
- **R7. Beside the playground and the blog**, keeping temperlang.dev's addresses.
- **R8. Link checking**, as strict as today's.
- **R9. Versioned docs**, a set per release, which we'll want once there are users on older releases.
- **R10. Polish:** good styles, a table of contents on each page, and the other bells and whistles, without our having to build each one.

|---|---|---|---|---|

Alerts need a remark plugin. | Python-Markdown, not CommonMark: nested lists need four spaces, and more. Alerts and `<details>` need plugins. | pulldown-cmark 0.13. `> [!NOTE]` alerts built in since 0.5, raw HTML passes through. Mermaid needs a preprocessor. | GFM conformant, with alerts and Mermaid done by the build. |

| R5 Fit | Node and React, a large dependency tree. | Python. | One Rust binary. | Python plus Kelpto via `temper`. |

No per-page table of contents or search yet; each extra is ours to build. |

**Docusaurus** is the strongest general-purpose site: versions, search, and a blog come built in.
But it fits our goals worst.
Its default MDX parsing rejects HTML comments, which this proposal's markers depend on, so it would need CommonMark mode everywhere.
It wants a Prism grammar and a large Node toolchain.
And its features are in React, which we'd need to learn and theme to match the playground.

**MkDocs** built the old site, but I don't recommend going back.
MkDocs 1.x is unmaintained, MkDocs 2.0 drops the plugins Material depends on, and Material itself is in maintenance mode while its team builds Zensical.
Its Markdown dialect is also furthest from GFM.
Zensical might be worth another look once it settles.

**mdBook** fits best of the three.
It's a single Rust binary, parses Markdown with pulldown-cmark, has GitHub's alert syntax and search built in, and its preprocessor protocol would let `temper` itself run inside the build.
Its `{{#include file:anchor}}` and `mdbook test` are prior art for named inclusions and checked examples.
Against it: it's book-shaped, it needs a highlight.js grammar for Temper, it has no versioning, and its 0.5 release broke the preprocessor API, so third-party preprocessors may lag.

The Kelpto-built site does R1, R3, R7, and R8 better than any of the three, because it was built for exactly our files.
Its weakness is R10: every bell and whistle, starting with search and a table of contents on each page, is ours to build and keep up.

I recommend keeping the Kelpto-built site for now and adding search and per-page tables of contents, while watching how much effort polish costs.
Making the doc tooling materialize everything into plain GFM keeps the publisher choice open.
If polish becomes a burden, mdBook is the one to move to, and nothing in the docs would need to change.

## Rationale

**Why HTML comments for markers?**
They're invisible on GitHub, survive every GFM parser as HTML blocks, and the first compiler used them, so the old `<!-- snippet: … -->` sources are easy to bring over.
Alternatives:

- *Heading anchors as names* need no markup, but a name changes when a heading's wording does, and a fragment can't be smaller or larger than a heading's section.
- *Link reference definitions* (`[//]: # (doc std/json)`) are also invisible, a common hack, but harder to read and easy to mangle.
- *One file per fragment*, which mdBook's and many sites' include mechanisms assume, scatters a module's docs and loses the point of literate files.
- *Directive syntax*, such as MyST's or remark's `:::`, isn't GFM, and shows up as stray text on GitHub.

**Why materialize instead of building?**
If inclusions and translations were filled in only when the site is built, the files on GitHub would have holes in them, and nobody would see in review that a std change altered three docs pages and a Python translation.
Committing the output costs disk and diff size, and gains a docs page that is the truth wherever it's read.

**Why a name and not a path?**
Names let a fragment move between files, which happens as std is reorganized, without breaking pages, links, or `help` calls.

**Why qnames for entities?**
They already exist, every declaration has one, and they're already stable identifiers that the backends and `temper.keep` rely on.
Inventing a second naming scheme for docs would give each entity two names to keep in sync.

**Why `[Name]` links, materialized?**
Javadoc's `{@link}` and rustdoc's intra-doc links show that writers will link a lot more when a link costs only a name.
Bare `[Name]` is how rustdoc spells it, and it's plain Markdown.
Materializing the definitions keeps the files working on GitHub, which rustdoc doesn't need to care about, but we do.

**Why move the checker into `temper`?**
A Python script in `compat/` works for this repository only.
Library authors writing literate Temper should get the same checks, and `temper doc` is already reserved for this.

## Compatibility

No Temper programs change.

- Existing docs keep working: a page with no markers is a page with no fragments.
- Kelpto's sanitizer drops HTML comments, and the site build requires each removal to be listed in `site/docs/removals.txt`.
  The build should drop `doc`, `include`, `translation`, and `example-*` comments itself, before rendering, so they don't need listing.
- `check_doc_examples.py`'s markers and `<!-- known: … -->` comments carry over unchanged.
- Making unmarked examples mean ✅ will fail tutorial steps that build on earlier ones until they're marked `continues`.
- Existing ```` ```temper ```` blocks in literate files are module code, and stay so.
  `example` is a new info-string word, which the literate reader must treat like `inert`: not part of the module.

## Implementation

1. A fragment index: parse each `.md` and `.temper.md` file under `docs/`, `lib/core`, and `lib/std`, and each doc comment in `.temper` files, and collect named fragments and declaration fragments by qname, reporting duplicate names, overlaps, and unclosed markers.
1. `temper doc check [--fix]` for inclusions, `include-each`, and cross-references.
1. Move `check_doc_examples.py` into `temper doc check`, then add `temper example` blocks, value and error comparison, continuations, and backends.
1. Translations, using the REPL's `translate` machinery, with `select`.
1. `help("fragment/name")` in the REPL, and fragment metadata on compiler-defined builtins.
1. Convert `docs/std/*.md` to inclusions from std's literate sources, which is the first real test of the whole thing, and removes the largest source of drift.
1. Search for the Kelpto-built site.

## Testing

- Fragment extraction: names, titles from headings, nesting, an unclosed marker at the end of a doc comment, a marker shown inside a code block that is not a marker, overlapping and duplicate names rejected.
- Declaration fragments: the autodoc rule's edge cases, a member's name, and an explicit marker that clashes with an implied name.
- Inclusions: stale text detected, `--fix` rewriting only the region between the markers and leaving the rest of the file byte for byte, heading options, nested inclusions, cycles rejected.
- Cross-references: a moved fragment's definitions rewritten, an unknown name reported, each step of relative resolution (a parameter, a sibling member, the module, imports, core), an ambiguous name rejected and fixed by qualifying it, and empty link text filled in.
- `include-each`: a new builtin appears, a removed one disappears, members are sorted.
- Examples: each marker with and without a value, an unmarked example that warns failing, a `temper example` in a literate file using a private helper while the module's own build doesn't see it, `continues` by name and by proximity, a backend list.
- Translations: a stale translation detected and regenerated, `select` of a declaration and of the top level, several languages.
- The whole `docs/` tree passes `temper doc check` in CI, as `check_doc_examples.py` does now.

## Open Issues

### Marker spelling

`doc:` or `snippet:`?
`snippet:` would let the first compiler's sources carry over unchanged, but "snippet" suggests code, and fragments are mostly prose.

### How fine-grained declaration fragments should be

Should every member get an implied fragment, or only exported ones?
Overloads and extension functions need a rule for their names.

### Translation churn

Every backend change that alters output alters the docs.
That's intended, but a large backend refactor could touch hundreds of translations.
Should `--fix` for translations be a separate step, so docs reviews aren't buried, or should translations be excluded from CI's freshness check and only regenerated at release time?

### Versioned docs

None of the options except Docusaurus and `mike` do versions.
Once there are users on older releases, do we publish a site per release, under `/0.6/`, or keep one site with "since 0.7" notes?

### Where the fragment index lives

The REPL's `help` needs the fragment index for std and core at run time.
The first compiler embedded a JSON resource built with the docs.
Should we do that again, compute it when std is settled, or read it from the docs tree when it's present?

### Std's docs: derived or parallel?

Some of std's documentation is for someone reading std's source, and some is general user documentation about its entities.
We could go either way:

- pull user docs out of std's literate sources, as proposed above, which keeps one copy but means std's source carries user-facing prose; or
- maintain parallel user documentation for std's types, which separates the audiences, at the cost of drift.

Establishing a convention for documenting library code would be good overall, especially if it extends to other libraries, which tips me toward the first.

### `example` or `usage`?

Which info-string word marks an example in a literate file?

### Link text for entities

When `--fix` fills in empty link text, what should it be for a type: `` `Boolean` ``, *class Boolean*, or *Boolean* in italics?
And should qualified references like `[Map.get]` show their qualification?

### Same repository as the compiler?

The docs live in the compiler's repository now, so one commit can change the language and its docs together, and one push builds the whole book.
That property is nice, but it may not be needed.

A separate book repository opens up options:

- GitHub Actions in the compiler's repository extract fragments, qnames, and translations from std and core into data files;
- the book repository takes those as a submodule, as the site takes the blog today, and so could the REPL;
- the book's own build, and its tooling choices, can change without touching the compiler.

The cost is that a language change and its docs need coordinated commits in two repositories, and "change something, push a button, get the whole book" goes away.
