# Go

**Hand-written illustration, not generated or run.** Temper has no Go
backend; this pretends it does (meeting point 1), to test both proposals
against a language without exceptions whose convention is
`(value, err)`. Strings are Go strings, Temper's `Int` is `int32`, and
classes are pointers to structs.

## Failure types

```go
package wherewith

// Error is implemented by every failure Wherewith reports.
// Use errors.As(err, &target) with a wherewith.Error target to catch them all.
type Error interface {
	error
	wherewithError()
}

// SqlProblem reports SQL text that Wherewith can't parse.
type SqlProblem struct {
	Text  string
	Word  int32
	msg   string
	cause error
}

func (p *SqlProblem) Error() string   { return p.msg } // "expected a table at word 4"
func (p *SqlProblem) Unwrap() error   { return p.cause }
func (p *SqlProblem) wherewithError() {}
```

- **Library base:** an interface with an unexported method, which only
  the package's types can implement, matched with `errors.As` (which
  accepts a pointer to an interface). Go's naming conventions make it
  `wherewith.Error`, not `wherewith.WherewithError`.
- **Category, without the single-inheritance conflict:** Go matching is
  by method, not by class, so a failure can match the library base and a
  category at once. For "invalid argument" Go has no general sentinel
  (`fs.ErrInvalid` is filesystem-flavored); a category the standard
  library does define, such as `errors.ErrUnsupported` (Go 1.21), would be
  joined with an `Is` method:
  `func (p *Unsupported) Is(target error) bool { return target == errors.ErrUnsupported }`.
- **Required:** `Error() string`, so a message always exists.
  **Cause:** `Unwrap()`, so `errors.Is` and `errors.As` look through it.
  **Equality:** none; Go compares only sentinels.
- **A sealed failure type** becomes an interface with an unexported
  method, its variants the structs that implement it; a type switch over
  them can't be checked for exhaustiveness by the compiler.

## Both proposals

As in Rust, Go's idiom is a failure value, so both proposals generate
the same code. Internally the generated functions return the concrete
`*SqlProblem`; the exported one converts to `error` with an explicit
`nil`, avoiding Go's typed-nil trap (a nil `*SqlProblem` stored in an
`error` isn't `nil`).

```go
type parser struct {
	words []string
	pos   int32
}

func (p *parser) select_() (*Select, *SqlProblem) { // `select` is a Go keyword
	if problem := p.keyword("SELECT"); problem != nil {
		return nil, problem
	}
	first, problem := p.name("a column")
	if problem != nil {
		return nil, problem
	}
	columns := []string{first}
	for w, ok := p.peek(); ok && w == ","; w, ok = p.peek() {
		p.pos++
		more, problem := p.name("a column")
		if problem != nil {
			return nil, problem
		}
		columns = append(columns, more)
	}
	// … FROM and the table the same way …
	if _, ok := p.peek(); ok {
		return nil, p.problem("expected the end")
	}
	return &Select{Columns: columns, Table: table}, nil
}

func (p *parser) need(message string) (string, *SqlProblem) {
	if w, ok := p.peek(); ok {
		return w, nil
	}
	return "", p.problem(message)
}

func (p *parser) problem(text string) *SqlProblem {
	word := p.pos + 1
	return &SqlProblem{Text: text, Word: word, msg: fmt.Sprintf("%s at word %d", text, word)}
}

// ParseSelect parses "SELECT a, b FROM t".
// On failure the error is a *SqlProblem.
func ParseSelect(text string) (*Select, error) {
	s, problem := (&parser{words: strings.Split(text, " ")}).select_()
	if problem != nil {
		return nil, problem
	}
	return s, nil
}
```

- **Declared failures** have no exceptions to map to here: the backend
  implements them as values, the same lowering the values proposal uses
  everywhere. Go is where declared failures cost the most backend work
  for the least difference.
- **Panics** are Go's `panic`; Temper code never recovers them.
- **A `Must` form** (`MustParseSelect`, panicking, as `regexp.MustCompile`)
  isn't generated by default; see the
  [naming rule](../claude-common-ground.md#naming-across-failure-styles).
- **Host callbacks:** a Go implementation of a Temper interface method
  that can fail returns `(T, error)`; an error that isn't one of the
  method's declared failure types is a panic in Temper, under either
  proposal.

**Which types can be failures (meeting point 6).** Under values with any
type allowed, a `String` failure needs a generated type with an
`Error()` method to be returned as `error`; with only declared failure
types (declared proposal, combined form), every failure is already such
a type.
