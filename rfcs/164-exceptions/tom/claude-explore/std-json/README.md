# Case: std JSON parsing and decoding

Temper's `std` has a JSON module: `parseJson` builds a syntax tree, and
a `JsonAdapter<T>` (written by hand, generated by the `@json`
decorator, or implemented in host code) decodes a tree into a `T`.
Both bubble. The parser finds a message for bad syntax, keeps it in the
producer's `jsonError`, and `parseJson` drops it ("TODO: if there is a
syntax error, produce it"). Decoding bubbles through `as` casts and the
builtin `toInt32`, so a caller can't tell bad syntax from a wrong type
deep inside, or from an Int32 overflow.

The excerpt cuts JSON down to integers, strings without escapes, and
arrays, and keeps the parser, the adapter interface, the Int32, String,
and List adapters, and a `decodeJson` that combines parsing and
decoding.

## How each design reads

Text to value, where two kinds of failure meet:

```temper
// Today (runnable)
export let decodeJson<T>(text: String, adapter: JsonAdapter<T>): T throws Bubble {
  adapter.decodeFromJson(parseJson(text))
}

// A, runnable today: 15 lines of nested `when`, re-wrapping each
// failure as the wider JsonProblem.

// A with a propagation operator that widens (HYPOTHETICAL)
export let decodeJson<T>(text: String, adapter: JsonAdapter<T>): Result<T, JsonProblem> {
  Ok(adapter.decodeFromJson(parseJson(text)?)?)
}

// B (HYPOTHETICAL)
export let decodeJson<T>(text: String, adapter: JsonAdapter<T>): T throws JsonProblem {
  adapter.decodeFromJson(parseJson(text)!)!
}

// C (HYPOTHETICAL)
export let decodeJson<T>(text: String, adapter: JsonAdapter<T>): T throws JsonSyntax, JsonShape {
  adapter.decodeFromJson(try parseJson(text))
}
```

Adding context on the way up (the list adapter puts the index in front
of the path), A runnable:

```temper
is Failed<T, JsonShapeError> -> return new Failed<List<T>, JsonShapeError>(
  new JsonShapeError("[${i.toString()}]${r.error.path}", r.error.expected)
);
```

So `decodeJson("[[1, 2], [\"3\"]]", ints)` fails with "at [1][0]:
expected an Int32", where today it fails with nothing.

## What host code sees

| | Python | Java | Rust |
|---|---|---|---|
| Today | `RuntimeError()`, or `ValueError` from `int()` | `RuntimeException`, or `NumberFormatException` | `Err(Error(None))`, or `Err(Error(Some(ParseIntError)))` |
| A, runnable | a `Failed` whose `error` is a `JsonShapeError` with `path` and `expected` | `Result<…, JsonProblem>`; `instanceof` | a generated `Result_` |
| B | a generated `JsonShapeError` (subclass of `JsonProblem`) with a message | the same | `Result<…, JsonProblem>` (an enum) |
| C | a generated `JsonShape`, no message or path | the same | `Err(Kind::JsonShape)` |

## Notes

- **Two failure types in one function** is Mike's hard case. Here both
  are declared together, so a sealed `JsonProblem` over
  `JsonSyntaxError` and `JsonShapeError` works under A and B. If they
  came from different libraries, a third type would have to wrap both.
  C lists both kinds (`throws JsonSyntax, JsonShape`).
- **Interfaces fix the failure type for every implementation.**
  `JsonAdapter.decodeFromJson` is implemented by hand, by generated
  code, and by host code; under A and B its failure type is part of
  that contract in every language, and changing it later is a breaking
  change.
- **`as` becomes a check.** Today `(t as JsonArray)` bubbles; under A
  the code tests `t is JsonArray` and fails with what it expected.
  That's also where the useful message comes from.
- **Generic matching works today:** `is Failed<T, JsonShapeError>`
  inside a generic class, and a `when` on the sealed `JsonProblem`
  without `else` (non-generic sealed types are exhaustive).
- **A tempest quirk met on the way:** a helper declared to return
  `Never<JsonSyntaxTree>` (always bubbling) type-checks and runs on the
  interpreter, but the Python and JS backends reject the branch that
  uses it as a value ("the returned value is Void"), so today's version
  calls it and then `bubble()`s.
- **Size:** 134 code lines against 91 today, nearly all in propagation
  and re-wrapping; the hypothetical `?` brings it back near today's.

## Precedence

- `decodeJson(t, a) ?? fallback == other` and `… orelse fallback ==
  other` both group the `==` into the fallback (see the
  [overview](../README.md#operator-precedence)).
- In `Ok(adapter.decodeFromJson(parseJson(text)?)?)`, each `?` applies
  to the call just before it. That needs postfix `?` to bind tighter
  than anything but `.` and calls, and a call after it to stay possible:
  `parseJson(text)?.elements` would lex as today's null-safe `?.`.
- With a prefix `try` (C), `try parseJson(text)` inside an argument
  list covers only that call; the outer `decodeFromJson` call needs its
  own `try` before `adapter`, where it then covers the whole
  expression. Which calls a prefix covers needs a rule (Swift: all of
  them to the right).
