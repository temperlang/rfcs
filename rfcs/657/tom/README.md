A list of things I think we need for making tempest the new temper. Some of this
might repeat things I've heard from other people on the team:

- Verify that so sensitive content remains.
  - If so, scrub history again.
  - Some less than ideal things can be edited without history scrubbing. It
    depends on team review to decide what matters.
- Maybe clean up notes or docs or other things.
  - It's *not* required to have all documentation perfect.
  - It's also not required that all docs be generated by ideal processes yet.
  - We should still do a pass to update docs to document new temper (tempest) in
    cases where old docs don't actually apply any more.
- Change all reference to "tempest" to saying "temper".
  - This includes "Tempest" or "TEMPEST" or other variations to their equivalent
    variations under the correct name.
- Pass at least the same tests in these libraries:
  - chromarite
  - hrefine
  - kelpto
  - ordable
  - temper-regex-engine
  - temper-regex-parser
  - wherewith
  - ... additional private libraries ...
  - ... others? ...
  - Some of these might suggest new tests required in tempest before becoming
    temper.
  - I'm already prioritizing tempest for temper library dev, but I've also been
    checking against kotlin temper. After full transition, the latter is no
    longer necessary.
- Review all open temperlang/temper issues and PRs for which should remain open.
  - Some bugs may have been fixed already in tempest.
  - PRs as they stand would be innapropriate for the new code base.
  - So we should ensure that we either close all PRs or have an issue for each.
  - If we have a good issue open for anything relevant, we can close the PR.
  - Issues under temperlang/temper point to RFCs under temperlang/rfcs.
- Further testing:
  - At least run another agent self-audit following all of the above.
  - What manual testing or review of testing do we want?
  - We should at least brainstorm what negative testing we want in addition to
    positive testing.
  - How can we describe constraints on behavior in a way that's clear to human
    reviewers?
  - We don't need final answers for all of the above, but we should at least
    consider and document what level is acceptable for initial usage as temper.
- Process:
  - Update issues and PRs per the above.
  - Put the new history on a branch on temperlang/temper.
  - Use old temper so stars or bookmarks find active dev.
  - Swap old main out and new main in by renaming branches.
